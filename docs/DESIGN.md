# Design — Decision Record & UX Notes

`ARCHITECTURE.md` says *what* the system looks like. This file says *why*
it looks that way — the alternatives considered and the trade-offs made.
Treat each section as an ADR (Architecture Decision Record) in miniature.
This is what makes you sound deliberate in an interview instead of
reciting a structure you didn't reason about.

## ADR-1: Agent framework — LangGraph vs. hand-rolled ReAct loop

- **Options considered**: LangGraph (explicit state graph), a hand-rolled
  ReAct-style while-loop, CrewAI (multi-agent, rejected as overkill for a
  single-agent reviewer).
- **Decision**: LangGraph by default; fall back to a hand-rolled loop if it
  adds friction without adding clarity.
- **Why**: LangGraph gives an explicit, inspectable state graph that's easy
  to diagram and reason about in an interview, and matches the "nice to
  have" framework list in the job posting. A hand-rolled loop is simpler to
  debug and has zero framework overhead — legitimate if LangGraph's
  abstractions get in the way for a single linear agent.
- **Trade-off accepted**: extra dependency and learning surface, in
  exchange for a clearer mental model and a stronger framework-familiarity
  signal for the interview.

## ADR-2: LLM provider — Claude primary, Ollama swappable

- **Options considered**: Claude only, Ollama only, both behind an
  abstraction.
- **Decision**: `LLMClient` protocol in `llm/base_client.py`; Claude is the
  default, Ollama is a drop-in alternative selected via config/UI.
- **Why**: Claude gives the strongest reasoning quality for a review this
  structured, and is explicitly named in the job posting. Ollama
  demonstrates awareness of cost, latency, and data-privacy trade-offs
  between hosted and local models — a real concern for internal tooling.
- **Trade-off accepted**: slightly more code (an interface plus two
  implementations) for a stronger "I thought about this" story.

## ADR-3: API execution model — synchronous vs. async job queue

- **Options considered**: synchronous request/response, async with a job
  ID + polling, websocket streaming of the trace.
- **Decision**: synchronous for v1.
- **Why**: simplest to build, test, and demo; LLM calls in the 10-30s range
  are tolerable for a single-user prototype with a UI spinner.
- **Trade-off accepted**: won't scale to concurrent users or long-running
  reviews. Documented in README as the first thing to change for
  production (job queue + polling, or websocket trace streaming so the UI
  can show tool calls *as they happen* instead of after the fact).

## ADR-4: Output contract — structured JSON vs. free-form markdown from the LLM

- **Options considered**: ask the LLM to write markdown directly; ask the
  LLM to return structured JSON/tool-call output and render markdown in
  code.
- **Decision**: structured output (see `PROMPTS.md` schema), rendered to
  markdown/HTML by `report_renderer.py`.
- **Why**: structured output is testable (you can assert on `severity`
  values, not regex-parse markdown), and lets the same data drive three
  different renderings — CLI text, UI components, and downloadable
  markdown/HTML — without re-prompting the LLM per format.
- **Trade-off accepted**: more upfront schema design work, in exchange for
  testability and reuse across all three interfaces.

## ADR-5: No persistence layer in v1

- **Options considered**: SQLite for review history, in-memory only.
- **Decision**: in-memory / ephemeral per-request; no database.
- **Why**: keeps the prototype's surface area focused on the agentic core,
  which is what's being evaluated. A history/dashboard feature is a
  believable "future improvement," not a v1 requirement.
- **Trade-off accepted**: no review history across sessions in the UI.

## ADR-6: Planner vs. Orchestrator separation (Deviation from PROMPTS.md)

- **Options considered**: Use a single monolithic prompt (as specified in `PROMPTS.md`) that outputs both a plan and a massive structured JSON review payload at once; OR separate the file selection (`planner_node`) from the deep-dive ReAct review and final synthesis (`review_node` / orchestrator).
- **Decision**: Separated `planner_node` (file selection only) from the final synthesis (Phase 6 Orchestrator).
- **Why**: Asking a single prompt to simultaneously output a comma-separated plan *and* the final JSON review breaks the directed graph flow (you can't plan and finalize in the exact same step). The prompt in `PROMPTS.md` is strictly used for the **Review Orchestrator (Phase 6)**, which will take all the raw markdown critiques generated by the `review_node` and synthesize them into the final structured JSON object.
- **Trade-off accepted**: Minor deviation from the literal text of `PROMPTS.md` which labeled the system prompt as "planner", in exchange for a clean, stable LangGraph pipeline that prevents context-window blowout.

## ADR-7: Local Model Selection for Agent Loop

- **Options considered**: `llama3.1`, `qwen2.5-coder:7b`, `llama3.2:3b`.
- **Decision**: `qwen2.5-coder:7b` is recommended as the primary local model; custom JSON fallback parsing is strictly required. Do not use Llama 3 family models for this specific agent loop due to context-processing timeouts and tool-calling hallucinations.
- **Why**: Extensive end-to-end testing revealed that local models struggle with the agent loop structure in different ways.

| Model | Size | Native Tool Calls? | Speed (E2E Run) | Grounding Accuracy |
|-------|------|--------------------|-----------------|--------------------|
| **qwen2.5-coder:7b** | 7B | No (Requires fallback parser) | ~1-2 minutes | High on obscure repos; Susceptible to "knowledge collapse" on famous repos (requires prompt mitigations). |
| **llama3.2:3b** | 3B | No (Requires fallback parser) | >3m00s (Timeouts) | N/A (Fails to complete synthesis step due to HTTP timeouts). |
| **llama3.1** | 8B | No (Hallucinates fake responses) | >3m00s (Timeouts) | N/A (Consistently times out processing large file contexts). |

`llama3.1` and `llama3.2:3b` both consistently fail to use native tool-calling features when provided with an OpenAPI schema, hallucinating JSON function calls into their text output instead. Furthermore, they are both extremely slow at processing the large `tests/main.py` context window (>16,000 characters), resulting in `httpx` timeouts (even with an extended 180s limit). We note that `llama3.2:3b` timing out just as badly (if not worse) than the 8B model is an unexplained oddity, as a smaller model should theoretically process context faster; we flag this as a known quirk but have not investigated further. `qwen2.5-coder:7b` also struggles with pure native tool calling, but consistently outputs parseable JSON tool invocations within its text blocks which the `OllamaClient` successfully captures via a fallback JSON parser. Most importantly, it is significantly faster and can successfully complete the file reviews.
- **Trade-off accepted**: Relying on a fallback parser for a smaller local model rather than achieving pure native tool calling, to enable local, free testing without paying for Claude API credits.

## ADR-8: Knowledge Collapse Failure Mode in Small Models

- **Options considered**: Leaving system prompts standard; switching exclusively to larger models; implementing aggressive post-generation safeguards.
- **Decision**: Implemented a combined strategy: prompt-level grounding as a best-effort layer ("ONLY review the exact code provided", "DO NOT rely on prior knowledge") plus a deterministic post-generation trace-consistency check as the primary safety net. We specifically avoided forcing the LLM to extensively quote source material in its reasoning, as this caused generation timeouts on large files (e.g., >3m on 8000-char context).
- **Why**: During E2E testing on `fastapi/fastapi` PR #1, `qwen2.5-coder:7b` correctly fetched `tests/main.py` via the tool loop, but its final review hallucinated a patch for `encode/httpx` and `http3/utils.py`. A controlled test against an obscure, zero-traffic repository (`jasmeet2000/ai-pr-reviewer`) with the exact same codebase and prompts yielded a perfectly grounded review. This isolated the failure not as a prompt-construction bug (the tool output was reaching the LLM), but as **"knowledge collapse"** — the model's pre-trained weights for a famous repository overwhelmed the provided tool context, causing it to aggressively pattern-complete hallucinated testing code. Stronger prompt-level constraints (like forcing the model to quote the file first) mitigated the hallucination but proved non-viable on local hardware due to severe timeouts caused by excessive token generation. Therefore, we rely on a light prompt constraint and a deterministic code-level check (matching referenced file paths in the generated review against the `state.trace` of actually fetched files) to flag ungrounded output.
- **Trade-off accepted**: Accepting that small local models will occasionally hallucinate on famous repos despite prompt mitigations, and that processing large contexts (e.g., >8000 chars) may hit hardware-bound timeouts during synthesis. We are not pursuing a 100% guarantee; truncation, duplicate-call prevention, and the grounding prompt form the final mitigation strategy, with the trace validation acting as the production safety net.

## UX notes — Streamlit UI

- **Information hierarchy**: input form (repo, PR, provider) at the top,
  collapsed by default once a review is running; trace view in the middle
  (so the "thinking" is visible while waiting, not hidden behind a
  spinner); final rendered review at the bottom, with severity-coded
  findings.
- **Trace view**: render as a simple vertical timeline — one row per tool
  call, showing tool name, a short arg summary, and a one-line result
  summary. Don't dump raw JSON; summarize it. This is the "wow, I can see
  the agent thinking" moment — worth getting right.
- **Severity color coding**: Critical = red, High = orange, Medium =
  yellow, Low = gray. Consistent between the UI badges and the markdown
  report (e.g. bold + label, since markdown has no color).
- **Buttons**: "Download report" (markdown or HTML) and "Post to GitHub"
  are separate, explicit actions — never post automatically just because a
  review finished. Mirrors the `--post-comment` flag being explicit in the
  CLI (see `SECURITY.md`).
- **Errors**: surface the API's `{error, detail}` payload directly in the
  UI as a dismissible banner, not a generic failure message.

## ADR-9: Grounding check scope — structural vs. semantic

- **What we check**: The grounding check (`review_agent.py`) scans the
  review text for file/path references and verifies every one was
  actually fetched during the tool-calling loop. This catches
  hallucinated file/repo references reliably.
- **What we don't check**: Whether the review's *claims* are semantically
  grounded in the file's content — i.e., whether findings cite specific
  functions, lines, or logic rather than generic best-practice advice.
- **Why not**: Semantic grounding verification would require a second LLM
  call or embedding-based similarity check, adding latency and cost
  without a clear accuracy bar. For v1, we document this as a known
  model-capability gap: `qwen2.5-coder:7b` tends to produce structurally
  correct but generic findings; Claude produces more specific reviews on
  the same inputs.
- **Trade-off accepted**: Structural grounding catches the most dangerous
  failure mode (hallucinated references leading to false findings).
  Specificity is a quality-of-review issue, not a correctness issue.
- **Finding-level Validation**: `review_generator.py` validates EVERY
  finding's `file` property against the complete set of fetched files (from
  `trace` and initial `files_to_review`). Any finding that references an
  un-fetched file is stripped and replaced with an Info placeholder, ensuring
  hallucinated files never leak into the final structured report.

## ADR-10: Post to GitHub UX vs. Synchronous API constraint

- **Trade-off**: The original `DESIGN.md` called for a separate, explicit "Post to GitHub" action after reviewing the generated report. However, because the `POST /review` API is fully synchronous (stateless) and can take 3-6 minutes with local Ollama, requiring a second click to post would mean either re-running the entire expensive generation pipeline or persisting the review state in a backend database (violating ADR-5: No persistence layer in v1).
- **Decision**: Move the "Post to GitHub" action into the initial submission form as a checkbox. 
- **Consequence**: The user commits to posting before seeing the generated review. We accept this deviation for the prototype to avoid complex state management or backend persistence, while retaining the ability to skip posting during dry-run reviews.

### Phase 10: Streamlit UI
- The Streamlit UI consists of an entry `app.py` mapping to components (`review_form`, `trace_view`, `review_display`, `error_banner`, `download_actions`) orchestrated by a typed `state.py` store and a simple HTTP client (`api_client.py`).
- **ADR-10**: Due to the stateless synchronous backend constraint, the "Post to GitHub" action was moved into the initial configuration form instead of being a post-generation step. This prevents a costly re-run against local LLMs.
- **Environment Note**: Phase 10 UI wiring was verified via a `MockLLMClient` due to the sandbox environment lacking Ollama access. A real live run using the actual local model was NOT completed in this session and remains the user's responsibility to verify locally before relying on this for a live demo.

## ADR-11: GitHub Action Live-Testing Scope Drop

- **Context**: Phase 12 originally planned to provide and verify a reusable `.github/workflows/review-action.yml`.
- **Decision**: The GitHub Action is provided as a reference architectural extension, but live verification of the action was explicitly dropped from scope.
- **Why**: The action structurally requires a paid `ANTHROPIC_API_KEY` to run Claude inside standard GitHub runners (which lack native Ollama support). Executing it live conflicts directly with the project's strict free-only constraint (which mandated testing via local Ollama or mocked interfaces).
- **Trade-off accepted**: Adhering to the free-only constraint meant dropping the live end-to-end verification of the GitHub Action integration, leaving the CLI and UI as the two fully tested, free, Ollama-backed entry points.
